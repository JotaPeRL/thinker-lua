# Lua API Reference

This is the self-contained reference for writing or modifying Thinker's
Lua AI: the engine data available over FFI, the full host API, the
idiomatic `lua/api/` wrappers, which AI modules exist today and what each
owns, the hook lifecycle that wires a Lua function into the game's own
decision points, the determinism rules the port must respect, and the
workflow for adding to or changing any of it. Together with
`docs/LUA_PORTING.md` (per-function provenance/drift tracking), this file
should be everything needed to work on the Lua AI as a modder would —
`IMPLEMENTATION_PLAN.md`/`IMPLEMENTATION_DETAILS.md`/`DEVELOPMENT_DIARY.md`
are this project's own internal roadmap/status/history, useful for *why*
a past decision was made but not required reading to write new AI code.
For a worked example, see `lua/examples/hello_ai.lua`.

## Layering

```
lua/ai/*.lua    -- the ported AI itself: tech, social, war, build, move,
                   plan, probe. Never requires `ffi` directly (enforced
                   by the sandbox) -- all engine access goes through
                   lua/api/.
lua/api/*.lua   -- idiomatic modules documented below: thin wrappers
                   over lua/ffi/, with real Lua booleans, named-field
                   tables, and bounds-checked accessors. Built on demand,
                   per module, as each porting item needed it -- coverage
                   intentionally lags what `ai/` doesn't need yet.
lua/ffi/*.lua   -- the generated low-level layer: types.lua (cdefs +
                   validation, regenerated by tools/gen_ffi.cpp on every
                   build, never hand-edited) and funcs.lua (the
                   LuaHostApi binding — every `extern "C"` function
                   pointer the C++ side exposes, api_version-checked at
                   load).
```

Reads of already-mapped engine structs are direct FFI (safe: a bad
layout is caught by startup validation, not a wild write). All writes to
engine state and all calls to engine functions go through
`lua/ffi/funcs.lua`'s wrappers around the `LuaHostApi` struct of function
pointers — never hand-declared calling conventions, never a raw pointer
crossing out of `lua/ffi/`. `ai/` modules only ever see IDs (`veh_id`,
`base_id`, `faction_id`) and FFI struct/cdata values, never bespoke
object graphs.

## Determinism rules

- **RNG:** `rand.game(n)` (the engine's main stream, `game_randv`,
  `0..n-1`) and `rand.map(low, high)` (the mod's own LCG, `random_get`,
  used by mapgen and some AI planning) are the *only* sanctioned sources
  of randomness in `lua/ai/`. `math.random`/`math.randomseed` raise at
  the runtime level specifically to force this — a decision that doesn't
  route through the engine's own RNG can't reproduce the C++ AI's
  behavior turn-for-turn. `rand.game_state()`/`rand.map_state()` (plus
  the `_draws` counters) are read-only peeks for Phase 5.3.5 determinism
  diagnostics — they never consume a stream themselves.
- **Integer semantics:** C truncates division/modulo toward zero; Lua's
  native `/`/`%` floor. `cmath.idiv(a, b)`/`cmath.imod(a, b)` give C
  semantics — bare `/`/`%` on integers are banned in `lua/ai/`. Bitwise
  work uses LuaJIT's `bit` library (available as a global in `ai/`
  modules, no `require` needed), with `bit.tobit`/`bit.band`/etc. where
  the original C++ relies on 32-bit wraparound.
- **Float narrowing:** Lua numbers are always doubles; C++ `float`
  locals narrow on every assignment. Where the original genuinely
  computes in `float` (rare — `select_build`'s `Wbase`/`Wthreat` block is
  the one confirmed live case), the port must use plain `/`, not `idiv` —
  the mirror-image trap of the integer rule above.
- **Iteration order:** no AI decision may depend on Lua hash-table
  (`pairs`) iteration order. Where the original iterates an
  `unordered_map`/`std::set` and the *set* of results (not the visiting
  order) determines the outcome, collect every candidate into a plain
  array first, then `table.sort` — this is the established pattern for
  the project's several priority-queue ports (`land_raise_plan`'s
  `point_max_queue_t` in `lua/ai/move.lua`, `design_units`'s
  `score_max_queue_t`/`score_min_queue_t` in `lua/ai/plan.lua`) — read the
  `table.sort` comparator at each of those call sites for the exact
  tie-break rule; it is written out explicitly in the code, not just
  implied by the original's map/set ordering.
- **The `and`/`or` ternary idiom is unsafe when the "then" branch can be
  a Lua boolean** (`cond and A or B` silently returns `B` whenever `A` is
  `false`, not just when `cond` is) — numbers are fine (Lua's `0` is
  truthy, unlike C), but a genuine two-boolean-branch ternary needs an
  explicit `if`/`else`. This exact class of bug has recurred twice in
  this project (`IMPLEMENTATION_DETAILS.md` 4.16, 4.18) — grep for
  `and .* or` around any boolean-valued expression before trusting it.
- **A related, distinct trap:** several `lua/ffi/funcs.lua` wrappers
  already convert the host API's raw `int32_t` into a real Lua boolean
  (`return api.x(...) ~= 0`) — re-comparing that result against `0`
  again (`== 0`/`~= 0`) is always false/always true respectively, since
  Lua never coerces between booleans and numbers. Check a wrapper's own
  body in `funcs.lua` before assuming it returns a raw int (`IMPLEMENTATION_DETAILS.md` 4.16 has the full incident this rule comes from).

## Hook lifecycle and classes

`lua/ai/init.lua` returns one flat table mapping hook name → Lua
function; `register_hooks()` (`src/luaai.cpp`) loads it on every (re)load
and resolves each entry into a Lua registry reference — no per-call
string lookup at runtime. A hooked C++ call site checks its hook once
and either uses the Lua-proposed result or falls through to the original
C++ body, depending on class:

| Class | Contract | C++ mechanism | Fallback on error |
|---|---|---|---|
| **1 — Pure query** | Lua returns a value, C++ uses it. No mutation beyond RNG draws. | `lua_ai_hook(name, out, out_count, {args...})` | Always safe — nothing happened yet. |
| **2 — Transactional** | Lua returns a *proposal*; C++ validates and applies it. Lua performs no mutation itself. | Same `lua_ai_hook`, C++-side validates the returned value before using it (e.g. `select_build`'s legality check). | Safe — propose-then-commit means nothing was mutated before the error. |
| **3 — Command/effect** | Lua calls host-API mutators directly as it runs; C++ has no separate commit step. | `lua_ai_command_hook(name, out, veh_id)` / `lua_ai_command_hook_faction(name, faction_id)` / `lua_ai_command_hook_base(name, out, base_id)` | **None once the first mutation is issued** — the wrapper finishes safely (e.g. `mod_veh_skip` for a per-vehicle hook) and reports "handled" rather than re-running the C++ body over partially-mutated state. Errors *before* any mutation still fall back normally. |

Three per-argument-shape variants of the Class 3 command hook exist
because their C++ callers have three different natural shapes, not
because Lua needs to know the difference: `lua_ai_command_hook` is
`(veh_id) -> int` (every per-vehicle mover); `lua_ai_command_hook_faction`
is `(faction_id) -> void`, return `false` meaning "not handled" and
anything else (including no return) meaning "handled" (`land_raise_plan`/
`invasion_plan`/`design_units`/`former_plans`); `lua_ai_command_hook_base`
is `(base_id) -> int` (`mod_base_hurry` — deliberately *not* a reuse of
the veh_id variant, since that one's error-after-mutation recovery calls
`mod_veh_skip` unconditionally, which would corrupt an unrelated vehicle
if a base_id flowed through it instead).

**Hook site is not always the call site.** Most Class 3 hooks wrap the
call site in the caller (`combat_move`/`land_raise_plan`/`former_plans`,
hooked where `move_upkeep`/`plans_upkeep` invoke them) — but a few wrap a
*sub-decision inside* the original function's own body instead
(`update_main_region`'s `prioritize_naval` tail, `probe()`'s `MOV_CHECK`/
`MOV_SABOTAGE`/`MOV_FRAME` fragments), when the decision isn't itself a
separately-callable function, or when hooking the whole function would
swallow unrelated fact-computation/UI code that has to stay in C++. See
`IMPLEMENTATION_DETAILS.md` 4.16/4.19 for the specific reasoning at each
site that needed this.

**Shadow mode** (`conf.lua_shadow`, Class 1/2 only): `lua_ai_shadow_call`/
`lua_ai_shadow_check` run the Lua side purely for comparison, snapshot/
restore both RNG streams around the call so the real C++ computation
that follows is unaffected, and log any divergence to `lua.log` as
`lua/cpp <hook> mismatch: ...`. Class 3 is never shadow-run (nothing to
compare once mutations happen) — its own validation path is a live
decision-trace diff instead (`IMPLEMENTATION_DETAILS.md` 5.1).

**Provenance:** every ported function has a `port.source` table entry
(file/func/`upstream_commit`) in its module — this is what
`tools/port_drift.py` reads to detect upstream C++ changes after a clean
merge. Add an entry (and a row in `docs/LUA_PORTING.md`) in the same
commit that ports the function.

## Engine data (`lua/ffi/types.lua`)

Generated by `tools/gen_ffi.cpp` from the engine's own struct headers,
regenerated on every build, never hand-edited (a header comment says so).
It has two parts:

1. **`ffi.cdef[[ ... ]]`** at the top of the file: plain C struct
   definitions (`typedef struct __attribute__((packed)) { ... } Name;`),
   directly readable — field names match the engine's own naming, and a
   struct only carries the fields some `lua/ai/`/`lua/api/` code actually
   reads (unused fields are `char _pad_N[k]` filler, not omitted — offsets
   must still match the real in-memory layout). Currently defined:
   `CTech`, `CFacility`, `CReactor`, `CAbility`, `CWeapon`, `CChassis`,
   `CArmor`, `UNIT`, `Continent`, `MFaction`, `CRules`, `Faction`, `BASE`,
   `VEH`, `CTerraform`. If the struct/field you need isn't there yet, add
   a `FIELD(...)`/`emit_struct` line to `tools/gen_ffi.cpp` — the file
   regenerates automatically as part of the normal CMake build.
2. **The returned table** (`return { globals = ..., counts = ..., enums =
   ..., validation = ... }`), loaded via `lua/ffi/validate.lua` (which
   also runs the `validation` list — every `sizeof`/`alignof`/`offsetof`
   check gen_ffi computed, asserted against LuaJIT's own `ffi.*` at
   startup — before returning `types`):
   - `types.globals` — fixed engine addresses (`Factions`, `Tech`,
     `Rules`, `CurrentTurn`, ...), each `ffi.cast` to the right pointer
     type once by the `lua/api/` module that owns it (`faction.lua`,
     `tech.lua`, `game.lua`, ...) rather than repeatedly by callers.
   - `types.counts` — array bounds (`MaxPlayerNum`, `MaxTechnologyNum`,
     `MaxProtoNum`, `MaxFacilityArrayNum`, `GrowthPopBoom`, ...) — always
     use these instead of a hardcoded literal when sizing a loop or
     bounds-check, since a rules/scenario change can move them.
   - `types.enums` — a flat lookup table of named constants (`FAC_*`,
     `DIPLO_*`, `ABL_*`, `PLAN_*`, `TRIAD_*`, `WMODE_*`, `GOV_*`,
     `BSTATE_*`, `PRB_*`, ...), added on demand as ported code needed
     them — **not** an exhaustive transcription of the original C++
     enums. `grep -n '<NAME> =' lua/ffi/types.lua` to check whether a
     constant is already exposed; if not, add it to `gen_ffi.cpp` next to
     the others of its kind (each hand-transcribed one carries a comment
     citing its C++ source line, since the headers that define them pull
     in `windows.h` and can't be included by gen_ffi's native host
     compiler).

Access pattern used throughout `lua/ai/`: `local E = types.enums`,
`local C = types.counts`, then `E.FAC_HEADQUARTERS`, `C.MaxPlayerNum`, etc.

## Host API (`lua/ffi/funcs.lua`)

The complete `LuaHostApi` surface: every engine read/mutation/call that
isn't a direct FFI struct-field read goes through here, one thin wrapper
per host function (`name = function(...) return api.name(...) end`) —
over 300 as of this writing. This is hand-written and hand-maintained (in
lockstep with `src/luaai.h`'s `LuaHostApi` struct and `src/luaai.cpp`'s
`host_*` implementations), unlike the generated `types.lua`. `HOST_API_VERSION`
at the bottom of the file is asserted against the C++ side's `api_version`
at load — a mismatch means the two sides were built from different
sources and Lua AI refuses to start rather than misread the struct.

Wrappers are near-mechanical passthroughs (rarely more than a raw
`~= 0`/boolean conversion — see the Determinism rules note above on
double-converting an already-boolean wrapper), grouped loosely by the
domain that first needed them: research/diplomacy (`is_human`,
`has_treaty`, `has_tech`, `tech_level`, `mod_tech_avail`, ...), social
engineering (`social_calc`, `society_avail`, `social_upheaval`, ...),
production (`mod_veh_avail`, `has_abil`, `has_fac_built`, `best_reactor`,
counts like `air_combat_units`/`land_combat_units`/`probe_units`, ...),
map/tile facts (`tile_region`, `is_ocean`, `map_range`, ...), movement
(`veh_at`, `mod_stack_check`, `set_move_to`, `search_route`, the
`TileSearch` iterator primitives, ...), probe (`mod_morale_veh`,
`aah_ooga`, `captured_leaders`, `probe_activate_check`, ...), and the RNG/
logging primitives that `lua/api/rand.lua`/`log.lua` wrap. **Do not call
`funcs.rand_game`/`funcs.rand_map` directly from `lua/ai/`** — go through
`lua/api/rand.lua`'s `rand.game`/`rand.map` instead, which is the same
call but keeps every RNG consumption point discoverable in one place.

To find any host function: `grep -n '<name> = function' lua/ffi/funcs.lua`
for the Lua wrapper, or `grep -n '<name>' src/luaai.h` for its C++
signature and the `host_*` implementation in `src/luaai.cpp` (the actual
engine-side behavior — the wrapper itself never does more than marshal
arguments). If what you need doesn't exist yet, adding a new host
function means: a field in `LuaHostApi` (`src/luaai.h`), a `host_*`
implementation and initializer-table entry (`src/luaai.cpp`), a matching
`cdef` field and wrapper in `funcs.lua`, and an `api_version`/
`HOST_API_VERSION` bump on both sides in the same change.

`lua/api/*.lua` (below) wraps the subset of `funcs.lua` that has an
idiomatic, named-field, real-boolean equivalent worth maintaining
separately — `lua/ai/` code calls `funcs.*` directly for anything that
doesn't have (or doesn't need) an `api/` wrapper, which is most of the
host API. Reach for `funcs.*` first when `api/` doesn't already cover
what you need; only add a new `api/` wrapper when several `ai/` call
sites would otherwise repeat the same non-trivial (multi-field,
struct-returning, or truthiness-converting) logic.

Deliberately minimal — bare globals, no faction/base/veh iteration (that
lives in `base`/`veh`/`faction` below).

|---|---|

| `game.multiplayer_active()` | Real boolean. |

### `map` — tile/continent facts (`lua/api/map.lua`)

| Function | Notes |
|---|---|
| `map.continent(region)` | Bounds-checked `Continent` cdata (`.tile_count`, `.pods`). |

### `log` — AI-facing logging (`lua/api/log.lua`)

| Function | Behavior |
|---|---|

| Function | Purpose |

## AI modules and registered hooks

`lua/ai/init.lua` is the ground truth for what is actually wired up — the
table below is a curated read of that file plus each module's own
header comment, current as of this writing. If in doubt, `lua/ai/init.lua`
itself is short and worth reading directly.

**"Live" has to be checked two different ways, and conflating them is a
real trap — this table originally got it wrong for `build.lua` and had
to be corrected.** A hook being *registered* in `init.lua` only means
`register_hooks()` resolved it into the Lua registry. What that
function's *own* named C++ call site does with it is one axis:
`lua_ai_hook`/`lua_ai_command_hook*` mean that specific call site uses
the Lua result whenever `lua_ai=1`; `lua_ai_shadow_call`/
`lua_ai_shadow_check` mean the C++ original at that call site *always*
runs and Lua is only ever compared against it for logging (gated by
`conf.lua_shadow`) — the C++ return value is what the game uses there,
unconditionally, regardless of `lua_ai`.

A shadow-only-labeled Lua function can *still* drive the game today,
through a second route: some already-live Class 2/3 hooks (`select_build`
is the case in point) are themselves ordinary Lua code that calls other
Lua functions directly — not through any host hook — as plain internal
helpers. If `find_proto`/`facility_score`/`governor_priorities`/etc. are
called *inside* `select_build`'s own Lua body (they are — verified by
grepping `lua/ai/build.lua` for internal callers, not by trusting either
function's own hook status), then editing them changes what
`select_build` actually returns, and that **is** live, even though each
of these functions *also* has its own separate, genuinely shadow-only
named hook (used only to validate C++'s stand-alone fallback body when
`select_build`'s hook fails or `lua_ai=0` — a parallel, secondary check,
not the primary way these functions affect the game). Don't infer "does
this affect gameplay" from a function's own hook-class row alone — grep
for who actually *calls* it in Lua first.

**As of 2026-07-31, `mod_tech_val`/`mod_tech_ai`/`mod_social_ai`/
`mod_wants_to_attack` were flipped from shadow-only to live** (`src/tech.cpp`,
`src/faction.cpp`) — the Consolidation gate (2026-07-14/16) had validated
all three modules byte-for-byte against C++ via shadow mode and formally
"closed" them, but left the actual C++ call sites on
`lua_ai_shadow_call`/`_check` rather than switching them to `lua_ai_hook`,
so `lua_ai=1` never actually made them decide anything — only
`lua_shadow=1` made them run at all, purely for comparison logging. That
gap is why this table originally (wrongly) listed them as inert; the fix
was a straightforward C++ change per function, following `select_build`'s
existing pattern exactly (try `lua_ai_hook` first, fall back to the
unchanged original body). `mod_social_ai`'s Class 2 wiring additionally
bounds-checks the unpacked `sf`/`sm2` pair before using them as array
indices (`src/faction.cpp`), since a hook return is an untrusted boundary
in a way the original C++-only computation never was.

The one hook that remains genuinely inert today is `combat_unit_early_return`
(`lua/ai/build.lua`) — see its row below.

## Developing or extending the Lua AI

**To change behavior in something that already drives gameplay**
(everything in the table above marked "Yes" — as of 2026-07-31 that's
every registered hook except `combat_unit_early_return`): edit the
function in its `lua/ai/*.lua` module directly — respect the hook's
Class contract (no mutation in a Class 1/2 function; a Class 3 function
may call `funcs.*` mutators freely, since there is no separate commit
step to protect) and the determinism rules above, then test (see below).
No C++ change is needed. Before assuming a `build.lua` function is
inert because its own row says "shadow-only", grep who calls it inside
`lua/ai/build.lua` first — most of them are reached from `select_build`.

**To change behavior in something that's genuinely inert today**
(only `build.lua`'s `combat_unit_early_return`, deliberately excluded
from `select_build`'s own Lua body — see its table row above): a
pure-Lua edit will show up as shadow-mode divergence logging (if
`conf.lua_shadow=1`) but has **no effect on actual gameplay** — the
matching `src/*.cpp` call site still needs its `lua_ai_shadow_call`/
`lua_ai_shadow_check` pair replaced with `lua_ai_hook` (or the relevant
`lua_ai_command_hook*`) before Lua's result is what the game actually
uses. Flipping it is a mechanical C++ change, the same one just applied
to `tech.lua`/`social.lua`/`war.lua`: try the hook first, keep the
existing computation as the fallback body, delete only the
now-redundant shadow-call/lambda scaffolding, and bump nothing
(`api_version` is for host-API struct layout, not hook wiring). Whether
it's *worth* doing for this specific one is a separate question — see
its own comment in `lua/ai/build.lua`/`select_build`'s definition for
why it was excluded from the live call graph in the first place (RNG
draw-count parity with C++, not a scoping decision that should be
casually reversed).

**To write genuinely new AI logic** (not a port of an existing C++
function): follow `lua/examples/hello_ai.lua`'s pattern — a module
returning named functions, registered by adding an entry to
`lua/ai/init.lua`'s returned table. A new *hook site* (a decision point
the C++ engine doesn't already call `lua_ai_hook`/`lua_ai_command_hook*`
at) additionally needs the C++ side wired up: pick the right macro for
the contract you want (table in "Hook lifecycle and classes" above), add
the call at the decision point, and give it a `port.source` entry (see
below) if it corresponds to an existing C++ decision being ported rather
than a wholly new one.

**Provenance:** when porting an existing C++ function (not writing new
logic), add a `port.source` entry in the module (file/func/
`upstream_commit`, see "Hook lifecycle and classes" above) and a row in
`docs/LUA_PORTING.md`'s table — that pair is what
`tools/port_drift.py` uses to detect upstream C++ changes to functions
this project has already ported.

**Testing loop:**

1. Build both presets and deploy (`Technical.md`'s "Building and running
   under Wine" section has the exact commands) — a `debug` preset if you
   need `debug.txt`/the Alt+D/M/V shortcuts.
2. Run the game (or `tools/autoplay_run.sh`/`tools/perf_run.sh` for an
   unattended multi-turn run) with `lua_ai=1`. For a shadow-only hook
   under active development, also set `lua_shadow=1` to get per-call
   divergence logging even though the C++ side still governs.
3. Check `lua.log` (game folder root) and, on debug builds, `debug.txt`:
   a Lua error is logged (deduplicated) rather than crashing the game,
   and any shadow-mode divergence appears as `lua/cpp <hook> mismatch:
   ...`. Both files truncate on every launch, so read them before the
   next run starts.
4. `log.debug(...)`/`log.ver(...)` (see the `log` module above) are the
   normal way to add your own visibility into a hook's decisions while
   iterating.
