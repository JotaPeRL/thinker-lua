# Lua API Reference

Reference for `lua/api/*.lua` (the idiomatic layer `lua/ai/*.lua` modules
are built on), the hook lifecycle that wires a Lua function into the
game's own AI decision points, and the project rules that keep the port
deterministic. See `IMPLEMENTATION_PLAN.md`/`IMPLEMENTATION_DETAILS.md`
for the full architecture and porting history — this file is the
day-to-day reference for writing or reading AI code, not a tutorial (for
that, see the "Hello AI" example once it exists, Phase 6 item 5).

## Layering

```
lua/ai/*.lua    -- the ported AI itself: tech, social, war, build, move,
                   plan, probe. Never requires `ffi` directly (enforced
                   by the sandbox) -- all engine access goes through
                   lua/api/.
lua/api/*.lua   -- idiomatic modules documented below: thin wrappers
                   over lua/ffi/, with real Lua booleans, named-field
                   tables, and bounds-checked accessors. Built on demand,
                   per module, as each porting item needed it -- coverage
                   intentionally lags what `ai/` doesn't need yet.
lua/ffi/*.lua   -- the generated low-level layer: types.lua (cdefs +
                   validation, regenerated by tools/gen_ffi.cpp on every
                   build, never hand-edited) and funcs.lua (the
                   LuaHostApi binding — every `extern "C"` function
                   pointer the C++ side exposes, api_version-checked at
                   load).
```

Reads of already-mapped engine structs are direct FFI (safe: a bad
layout is caught by startup validation, not a wild write). All writes to
engine state and all calls to engine functions go through
`lua/ffi/funcs.lua`'s wrappers around the `LuaHostApi` struct of function
pointers — never hand-declared calling conventions, never a raw pointer
crossing out of `lua/ffi/`. `ai/` modules only ever see IDs (`veh_id`,
`base_id`, `faction_id`) and FFI struct/cdata values, never bespoke
object graphs.

## Determinism rules

- **RNG:** `rand.game(n)` (the engine's main stream, `game_randv`,
  `0..n-1`) and `rand.map(low, high)` (the mod's own LCG, `random_get`,
  used by mapgen and some AI planning) are the *only* sanctioned sources
  of randomness in `lua/ai/`. `math.random`/`math.randomseed` raise at
  the runtime level specifically to force this — a decision that doesn't
  route through the engine's own RNG can't reproduce the C++ AI's
  behavior turn-for-turn. `rand.game_state()`/`rand.map_state()` (plus
  the `_draws` counters) are read-only peeks for Phase 5.3.5 determinism
  diagnostics — they never consume a stream themselves.
- **Integer semantics:** C truncates division/modulo toward zero; Lua's
  native `/`/`%` floor. `cmath.idiv(a, b)`/`cmath.imod(a, b)` give C
  semantics — bare `/`/`%` on integers are banned in `lua/ai/`. Bitwise
  work uses LuaJIT's `bit` library (available as a global in `ai/`
  modules, no `require` needed), with `bit.tobit`/`bit.band`/etc. where
  the original C++ relies on 32-bit wraparound.
- **Float narrowing:** Lua numbers are always doubles; C++ `float`
  locals narrow on every assignment. Where the original genuinely
  computes in `float` (rare — `select_build`'s `Wbase`/`Wthreat` block is
  the one confirmed live case), the port must use plain `/`, not `idiv` —
  the mirror-image trap of the integer rule above.
- **Iteration order:** no AI decision may depend on Lua hash-table
  (`pairs`) iteration order. Where the original iterates an
  `unordered_map`/`std::set` and the *set* of results (not the visiting
  order) determines the outcome, collect every candidate into a plain
  array first, then `table.sort` — this is the established pattern for
  the project's several priority-queue ports (`land_raise_plan`'s
  `point_max_queue_t`, `design_units`'s `score_max_queue_t`/
  `score_min_queue_t`), each with its own documented tie-break rule
  (`IMPLEMENTATION_DETAILS.md` 4.16/4.18).
- **The `and`/`or` ternary idiom is unsafe when the "then" branch can be
  a Lua boolean** (`cond and A or B` silently returns `B` whenever `A` is
  `false`, not just when `cond` is) — numbers are fine (Lua's `0` is
  truthy, unlike C), but a genuine two-boolean-branch ternary needs an
  explicit `if`/`else`. This exact class of bug has recurred twice in
  this project (`IMPLEMENTATION_DETAILS.md` 4.16, 4.18) — grep for
  `and .* or` around any boolean-valued expression before trusting it.
- **A related, distinct trap:** several `lua/ffi/funcs.lua` wrappers
  already convert the host API's raw `int32_t` into a real Lua boolean
  (`return api.x(...) ~= 0`) — re-comparing that result against `0`
  again (`== 0`/`~= 0`) is always false/always true respectively, since
  Lua never coerces between booleans and numbers. Check a wrapper's own
  body in `funcs.lua` before assuming it returns a raw int (`IMPLEMENTATION_DETAILS.md` 4.16 has the full incident this rule comes from).

## Hook lifecycle and classes

`lua/ai/init.lua` returns one flat table mapping hook name → Lua
function; `register_hooks()` (`src/luaai.cpp`) loads it on every (re)load
and resolves each entry into a Lua registry reference — no per-call
string lookup at runtime. A hooked C++ call site checks its hook once
and either uses the Lua-proposed result or falls through to the original
C++ body, depending on class:

| Class | Contract | C++ mechanism | Fallback on error |
|---|---|---|---|
| **1 — Pure query** | Lua returns a value, C++ uses it. No mutation beyond RNG draws. | `lua_ai_hook(name, out, out_count, {args...})` | Always safe — nothing happened yet. |
| **2 — Transactional** | Lua returns a *proposal*; C++ validates and applies it. Lua performs no mutation itself. | Same `lua_ai_hook`, C++-side validates the returned value before using it (e.g. `select_build`'s legality check). | Safe — propose-then-commit means nothing was mutated before the error. |
| **3 — Command/effect** | Lua calls host-API mutators directly as it runs; C++ has no separate commit step. | `lua_ai_command_hook(name, out, veh_id)` / `lua_ai_command_hook_faction(name, faction_id)` / `lua_ai_command_hook_base(name, out, base_id)` | **None once the first mutation is issued** — the wrapper finishes safely (e.g. `mod_veh_skip` for a per-vehicle hook) and reports "handled" rather than re-running the C++ body over partially-mutated state. Errors *before* any mutation still fall back normally. |

Three per-argument-shape variants of the Class 3 command hook exist
because their C++ callers have three different natural shapes, not
because Lua needs to know the difference: `lua_ai_command_hook` is
`(veh_id) -> int` (every per-vehicle mover); `lua_ai_command_hook_faction`
is `(faction_id) -> void`, return `false` meaning "not handled" and
anything else (including no return) meaning "handled" (`land_raise_plan`/
`invasion_plan`/`design_units`/`former_plans`); `lua_ai_command_hook_base`
is `(base_id) -> int` (`mod_base_hurry` — deliberately *not* a reuse of
the veh_id variant, since that one's error-after-mutation recovery calls
`mod_veh_skip` unconditionally, which would corrupt an unrelated vehicle
if a base_id flowed through it instead).

**Hook site is not always the call site.** Most Class 3 hooks wrap the
call site in the caller (`combat_move`/`land_raise_plan`/`former_plans`,
hooked where `move_upkeep`/`plans_upkeep` invoke them) — but a few wrap a
*sub-decision inside* the original function's own body instead
(`update_main_region`'s `prioritize_naval` tail, `probe()`'s `MOV_CHECK`/
`MOV_SABOTAGE`/`MOV_FRAME` fragments), when the decision isn't itself a
separately-callable function, or when hooking the whole function would
swallow unrelated fact-computation/UI code that has to stay in C++. See
`IMPLEMENTATION_DETAILS.md` 4.16/4.19 for the specific reasoning at each
site that needed this.

**Shadow mode** (`conf.lua_shadow`, Class 1/2 only): `lua_ai_shadow_call`/
`lua_ai_shadow_check` run the Lua side purely for comparison, snapshot/
restore both RNG streams around the call so the real C++ computation
that follows is unaffected, and log any divergence to `lua.log` as
`lua/cpp <hook> mismatch: ...`. Class 3 is never shadow-run (nothing to
compare once mutations happen) — its own validation path is a live
decision-trace diff instead (`IMPLEMENTATION_DETAILS.md` 5.1).

**Provenance:** every ported function has a `port.source` table entry
(file/func/`upstream_commit`) in its module — this is what
`tools/port_drift.py` reads to detect upstream C++ changes after a clean
merge. Add an entry (and a row in `docs/LUA_PORTING.md`) in the same
commit that ports the function.

## Module reference

### `game` — turn/global scalars (`lua/api/game.lua`)

Deliberately minimal — bare globals, no faction/base/veh iteration (that
lives in `base`/`veh`/`faction` below).

| Function | Returns |
|---|---|
| `game.turn()` | Current turn number (`*CurrentTurn`). |
| `game.rules()` | The `*GameRules` bitmask (plain int — distinct from `tech.rules()`, a whole `CRules` struct). |
| `game.cloud_cover()` | `*MapCloudCover`. |
| `game.sunspot_duration()` | `*SunspotDuration`. |
| `game.diff_level()` | `*DiffLevel`. |
| `game.map_area_sq_root()` / `game.map_area_tiles()` / `game.map_area_y()` | Map size scalars. |
| `game.faction_ranking(i)` | Faction id at ranking position `i` (`FactionRankings[i]`, an array, not a scalar). |
| `game.multiplayer_active()` | Real boolean. |
| `game.base_count()` | `*BaseCount` (also available as `base.count()`). |

### `map` — tile/continent facts (`lua/api/map.lua`)

| Function | Notes |
|---|---|
| `map.continent(region)` | Bounds-checked `Continent` cdata (`.tile_count`, `.pods`). |
| `map.bad_reg` | Opaque host query. |
| `map.base_at(x, y)` | Coordinate → `base_id`, or a sentinel if none. |
| `map.safety(x, y)` | Reads `mapdata` (the `PMTable`, an `unordered_map` that stays entirely host-side per Phase 4.3) — one-field read, not a general `mapdata` accessor. |
| `map.tile_is_base(x, y)` / `map.tile_owner(x, y)` / `map.tile_is_base_radius(x, y)` | Single-field tile reads (a `MAP*` itself never crosses into Lua). |

Most Movement code reads far more tile state than this via
`lua/ffi/funcs.lua` directly (`tile_region`, `tile_is_ocean`, dozens of
others) — `map.lua` only holds what predates that expansion; check
`funcs.lua` for anything not listed here.

### `path` — route queries (`lua/api/path.lua`)

| Function | Notes |
|---|---|
| `path.search_route(veh_id, x, y)` | `{found, tx, ty}` — `tx`/`ty` equal `x`/`y` unchanged if nothing was found. `TileSearch` itself is constructed and discarded host-side; only the result crosses into Lua. |

### `rand` — sanctioned RNG (`lua/api/rand.lua`)

| Function | Stream |
|---|---|
| `rand.game(n)` | Engine's main stream (`game_randv`), draws `0..n-1`. |
| `rand.map(low, high)` | The mod's own LCG (`random_get`). |
| `rand.game_state()` / `rand.mod_state()` / `rand.map_state()` | Read-only peeks, don't consume a draw. |
| `rand.game_draws()` / `rand.mod_draws()` / `rand.map_draws()` | Running draw counts (Phase 5.3.5 diagnostics). |

### `log` — AI-facing logging (`lua/api/log.lua`)

| Function | Behavior |
|---|---|
| `log.debug(fmt, ...)` | Always written to `lua.log` (mirrored to `debug.txt` when a debug build has one open). `string.format`-style if extra args are given, a raw string otherwise. |
| `log.ver(fmt, ...)` | Same, but only when `conf.debug_verbose` (the Alt+M toggle) is set — checked host-side, callers don't need to know about `conf`. |

### `cmath` — C-compatible arithmetic (`lua/api/cmath.lua`)

| Function | Purpose |
|---|---|
| `cmath.idiv(a, b)` / `cmath.imod(a, b)` | C truncating division/modulo — mandatory for integer arithmetic in `ai/` (see Determinism rules above). |
| `cmath.clamp(v, lo, hi)` | Mirrors the C++ `clamp()` helper used throughout the scoring code. |
| `cmath.popcount8(byte)` | 8-bit popcount (replaces `__builtin_popcount` on `TechOwners[]` bitfields, `MaxPlayerNum=8`). |

### `base` — BASE accessors (`lua/api/base.lua`)

`base.get(base_id)` re-fetches `Bases[]`'s current pointer via the host
API on *every call* (unlike `faction`/`tech` below, which cache one
`ffi.cast` for a fixed global) — `Bases`/`Vehs` are mutable, re-pointable
pointers, not fixed addresses.

| Function | Notes |
|---|---|
| `base.get(base_id)` | Bounds-checked `BASE` cdata. |
| `base.count()` | `*BaseCount`. |
| `base.plr_owner(base)` | `is_human(base.faction_id)`. |
| `base.gov_config(base)` | Real `governor_flags` for a human base; `0xffffffff` for AI bases (governors don't constrain AI). |
| `base.item(base)` | Currently-building item: `>=0` a unit_id, negative `-facility_id` (or below `-SP_ID_First`, a secret project). |
| `base.item_is_project(base)` / `base.item_is_unit(base)` | |
| `base.drone_riots_active(base)` / `base.drone_riots(base)` | `BSTATE_DRONE_RIOTS_ACTIVE` flag vs. the `drone_total > talent_total` fact. |
| `base.se_police(base_id, pending)` | Takes an id, not cdata (needs `has_fac_built` too). |
| `base.has_fac_built(item_id, base_id)` | |
| `base.former_tile_tally(base_id)` | `{num, sea}`. |
| `base.can_link_artifact(base_id)` | |

| Function | Notes |

| `faction.meta(faction_id)` | `MFaction` cdata (rule/scenario metadata, distinct struct from `Faction`). |
| `faction.is_human` / `faction.has_treaty` / `faction.climactic_battle` / `faction.mod_wants_to_attack` / `faction.society_avail` / `faction.has_project` / `faction.has_free_facility` / `faction.has_aircraft` / `faction.mineral_factor` / `faction.un_charter` / `faction.defense_modifier` / `faction.keep_fungus` / `faction.social_ai_bias` | Direct `funcs.*` re-exports — check `lua/ffi/funcs.lua` for exact signatures/return-truthiness. |
| `faction.social_calc(models, faction_id)` | `models` a 0-indexed `{[0]=,[1]=,[2]=,[3]=}` table; returns the 11 named `CSocialEffect` fields. |
| `faction.social_upheaval(faction_id, models)` | |
| `faction.psych_check(faction_id)` | `{content_pop, base_limit}`. |
| `faction.great_beelzebub` / `faction.great_satan` / `faction.has_agenda` / `faction.hq_region` | War-decision (item 2b) dependencies. |

### `veh` — VEH accessors (`lua/api/veh.lua`)

Same mutable-pointer re-fetch pattern as `base.get`. Most `is_*`
predicates are pure delegation to the matching `tech.proto_is_*` on
`veh.unit_id` — check the function body before assuming a VEH-level
override exists (`is_combat_unit` is the one exception: it adds a
`BSC_FUNGAL_TOWER` exclusion `Units[unit_id].is_combat_unit()` alone
doesn't have).

| Function | Notes |
|---|---|
| `veh.get(veh_id)` / `veh.count()` | |
| `veh.is_former` / `is_colony` / `is_probe` / `is_supply` / `is_transport` / `is_artifact` / `is_planet_buster` | Pure delegation to `tech.proto_is_*`. |
| `veh.triad(veh)` | |
| `veh.is_combat_unit(veh)` | `tech.proto_is_combat_unit` **and** `unit_id ~= BSC_FUNGAL_TOWER` — not pure delegation. |
| `veh.is_garrison_unit` / `is_police_unit` | |
| `veh.eval_garrison(veh)` | Triad + combat + armor scoring, engine_veh.h's own formula. |
| `veh.at_target(veh)` | Order/waypoint check — "has this vehicle reached where it's going". |
| `veh.in_transit(veh)` | |
| `veh.is_native_unit(veh)` | Fauna/alien-life check (`unit_id < MaxProtoFactionNum and offense < 0`) — native life is out of scope for AI decisions (user decision, 2026-07-20) but this predicate itself is still exposed. |
| `veh.plr_owner(veh)` | |

### `tech` — CTech/CFacility/CReactor/CWeapon/CChassis/CArmor/UNIT accessors (`lua/api/tech.lua`)

The largest module — owns every prototype/tech-table accessor, since
`design_units`/`select_build`/the tech-AI pilot all read deeply from the
same handful of fixed global tables.

| Function | Notes |
|---|---|
| `tech.get(tech_id)` | `CTech` cdata. |
| `tech.facility(facility_id)` | Bounds-checked against `MaxFacilityArrayNum`, **not** `MaxFacilityNum` — the latter undercounts (Secret Projects share the same array at higher indices). |
| `tech.ability(ability_id)` | `CAbility` cdata — only `.cost` is in the generated cdef (`cost_increase_with_armor()`/`_with_speed()` are one-liners over it, inlined at each call site rather than re-exposed as their own functions). |
| `tech.reactor` / `tech.weapon` / `tech.chassis` | Bounds-checked table accessors. |
| `tech.proto(unit_id)` | `UNIT` cdata, bounds-checked against `MaxProtoNum`. |
| `tech.proto_offense_value` / `proto_defense_value` / `proto_speed` | Re-port UNIT's own inline methods dropped by field-only cdef generation. |
| `tech.proto_is_missile` / `_planet_buster` / `_psi_unit` / `_colony` / `_prototyped` / `_active` / `_former` / `_probe` / `_supply` / `_transport` / `_artifact` / `_combat_unit` / `_armored` / `_garrison_unit` / `_police_unit` | Prototype-level predicates — `veh.is_*` for a given vehicle mostly delegates straight to these on `veh.unit_id`. |
| `tech.proto_triad` / `proto_range` / `proto_weapon_mode` | |
| `tech.proto_offense(unit_id)` / `proto_defense(unit_id)` | **Not** the same computation as `proto_offense_value`/`proto_defense_value` above — these apply the reactor multiplier and a planet-buster special case (`src/veh.cpp`'s own `proto_offense`/`proto_defense`, not `UNIT::offense_value()`/`defense_value()`). Easy to confuse; check which one a port actually needs. |
| `tech.proto_reactor_type(unit_id)` | Clamped `[1,4]` reactor tier, used by combat scoring to normalize damage. |
| `tech.owners(tech_id)` | Per-faction bitfield byte (`MaxPlayerNum=8` fits exactly). |
| `tech.rules()` | Whole `CRules` struct — distinct from `game.rules()`'s plain bitmask. |
| `tech.recycling_tanks()` | `{nutrient, mineral, energy}` — one `CResourceInfo`'s leading fields, not the whole struct. |
| `tech.has_tech` / `tech_level` / `tech_is_preq` / `mod_tech_avail` / `revised_tech_cost` / `tech_balance_enabled` | Direct `funcs.*` re-exports. |
